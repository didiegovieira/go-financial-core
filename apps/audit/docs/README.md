# Audit Worker

## Overview

The `audit` app is an asynchronous worker that turns events produced by the `core` app into queryable PostgreSQL records. It does not expose an HTTP API: its input is a Kafka consumer, and its state belongs to the `audit_db` database.

This context provides a technical trail of observed events without coupling audit persistence to the main financial transaction.

## Responsibilities

- Consume account and wallet topics published by `core`.
- Translate Kafka topics into known event names.
- Preserve the received JSON payload.
- Create and persist an audit record with its own UUID.
- Participate in the consumer's graceful shutdown lifecycle.

The worker does not modify accounts or wallets, publish new events, or expose endpoints for querying audit logs.

## Processing flow

```text
Kafka topic
    |
    v
Consumer -> handler -> RecordAudit -> AuditLogRepository -> audit_db.audit_logs
```

The handler receives the message `topic`, `key`, and `value`. The topic determines `event_name`, the key becomes `aggregate_id`, and the complete message value is stored as JSONB in `payload`.

## Consumed topics

The default consumer group is `audit-service`.

| Topic | Recorded event |
| --- | --- |
| `core.account.created` | `account.created` |
| `core.account.deleted` | `account.deleted` |
| `core.wallet.credited` | `wallet.credited` |
| `core.wallet.debited` | `wallet.debited` |

An unmapped topic results in an unknown-event error. When adding an event to `core`, also update `internal/infrastructure/messaging/kafka/topics.go` in this app.

## Persisted model

The `001_create_audit_logs.sql` migration creates `audit_logs` with:

| Field | Meaning |
| --- | --- |
| `id` | Audit record UUID generated by the worker. |
| `event_name` | Event name derived from the topic. |
| `aggregate_id` | Kafka message key, currently the account UUID. |
| `payload` | Complete JSON envelope published by `core`. |
| `occurred_at` | UTC time at which the use case processed the message. |
| `created_at` | Insertion time assigned by PostgreSQL. |

Indexes exist for `event_name`, `aggregate_id`, and `occurred_at`.

Important: `occurred_at` in this table represents worker processing time. The event's original timestamp remains available under `payload.occurred_at`.

## Configuration and execution

| Variable | Default | Purpose |
| --- | --- | --- |
| `POSTGRES_HOST` | `localhost` | PostgreSQL host outside Compose. |
| `POSTGRES_PORT` | `5432` | PostgreSQL port. |
| `POSTGRES_DATABASE` | `audit_db` | Audit trail database. |
| `KAFKA_BROKERS` | `kafka:9092` | Broker list. |
| `KAFKA_CONSUMER_GROUP_ID` | `audit-service` | Consumer group. |
| `OTEL_SERVICE_NAME` | module name | Worker name used in telemetry. |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://localhost:4317` | OTLP destination. |

Run directly when PostgreSQL and Kafka are available:

```bash
go run ./apps/audit/cmd/worker
```

Run the complete ecosystem:

```bash
docker compose up --build
```

The HTTP port field in the shared settings does not imply that this worker exposes an active API.

## Current limitations

- There is no endpoint for reading or searching audit records.
- There is no explicit deduplication by `event_id`; a reprocessed message may create another record.
- Retries, a dead-letter queue, and poison-message handling are not modeled in this app.
- The table stores the received envelope but does not validate each payload version internally.

## Where to make changes

- `cmd/worker`: executable entry point.
- `internal/application/usecase`: audit record creation.
- `internal/domain/entity`: the `AuditLog` domain model.
- `internal/infrastructure/messaging/kafka`: topics, handler, and consumer.
- `internal/infrastructure/database/postgres`: migration, mapper, and repository.
- `internal/runtime`: worker lifecycle and shutdown.
